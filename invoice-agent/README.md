# invoice-agent (milestone B1: local extraction)

Reads invoice PDFs locally, pulls out the key fields, flags anything a
human should check, and spots invoices that were sent twice. Everything
runs on your own machine. No cloud services, no paid APIs.

All invoices here are **synthetic**: made-up companies, numbers and
amounts, generated by `synthetic/generate_invoices.py`.

## What it does

| Part | File | What it does |
|---|---|---|
| PDF reading | `extractor/pdf_text.py` | pdfplumber text (plain and layout mode) and tables; detects a missing text layer |
| Fields | `extractor/fields.py` | One function per field: vendor, invoice_number, invoice_date, due_date, currency, line_items, subtotal, tax, total. Each returns value + confidence |
| Checks | `extractor/validate.py` | Flags: `missing_<field>`, `low_confidence_<field>` (< 0.7), `totals_mismatch`, `due_before_invoice_date`, `no_text_layer`. `needs_review = bool(flags)` |
| Duplicates | `extractor/duplicates.py` | Key = normalised vendor + invoice number + total (2 dp), stored in SQLite (`data/duplicates.db`) |
| Extractor API | `extractor/api.py` | FastAPI on port 8101 |
| Mock accounting | `mock_accounting/api.py` | **MOCK** QuickBooks-style API on port 8102 with **fake data** |
| Accuracy | `scripts/accuracy_report.py` | Compares extraction with `synthetic/expected.json` |

### Confidence rule

- `1.0` value found next to an expected label (e.g. `Invoice No:`)
- `0.6` no label; a fallback pattern found it (e.g. vendor from the letterhead line)
- `0.0` not found. The value stays `None`. Nothing is guessed.

Money fields (subtotal, tax, total) and the due date have **no fallback**:
a guessed total or due date is worse than a missing one.

### Dates

Dates are returned as ISO `YYYY-MM-DD`. Accepted: `2026-10-03`,
`03/10/2026`, `3 Oct 2026`. A slash date where both parts are 12 or less
(`03/10/2026`) is ambiguous; the extractor **assumes dd/mm** and lowers the
confidence to 0.6, so the invoice is flagged for review. If one part is
above 12 (`28/10/2026`) the order is clear and confidence stays at 1.0.

### Why not AWS Textract

Textract is not used. It is only available on the AWS Paid plan for new
accounts (checked 20 Nov 2026), and this project is $0 only. B1 uses
pdfplumber, which needs a text layer; scanned or image-only PDFs are
flagged `no_text_layer` instead of being read.

## Run it

```
cd invoice-agent
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
copy .env.example .env

.venv\Scripts\python synthetic\generate_invoices.py   # rebuild the 12 PDFs + expected.json
.venv\Scripts\python -m pytest -q
.venv\Scripts\python scripts\accuracy_report.py

.venv\Scripts\python -m extractor.api          # http://127.0.0.1:8101
.venv\Scripts\python -m mock_accounting.api    # http://127.0.0.1:8102 (MOCK)
```

### Extractor API (port 8101)

- `GET /health`
- `POST /extract` with either
  - multipart upload, form field `file`, or
  - JSON `{"path": "inv_01.pdf"}`; the path must be inside `INBOX_DIR`
    (paths outside it get 403)

  Returns `file_id`, `fields`, `confidences`, `flags`, `needs_review`.
- `POST /check-duplicate` with JSON
  `{"file_id", "vendor", "invoice_number", "total"}` returns
  `{"duplicate": bool, "original": file_id or null}`. The first time a key
  is seen it is stored.

### Mock accounting API (port 8102)

**This is a mock with fake data.** It does not connect to QuickBooks or
any real accounting system. Payment records in `mock_accounting/data.json`
are invented for the synthetic invoices.

- `GET /invoices/{invoice_number}/payment-status` returns
  `{"status": "paid" | "unpaid" | "partial", "amount_paid", "mock": true}`;
  unknown numbers return 404.
- Every response carries the header `X-Mock: true`.

## The synthetic invoices

12 PDFs in `synthetic/invoices/`, 4 layouts (classic ruled table,
two-column, letterhead with `Inv No.` labels and an unruled table, narrow
receipt), currencies USD / EUR / GBP / PKR. Special cases:

- `inv_09_resent_copy.pdf`: same vendor, number and total as `inv_01`
- `inv_10_no_due_date.pdf`: no due date printed
- `inv_11_malformed.pdf`: table cut off mid-row, no subtotal/tax, total printed as `##.#?`
- `inv_12_image_only.pdf`: the page is a picture, no text layer

The generator is deterministic (no randomness; reportlab invariant mode).
Re-running it produced byte-identical files on the machine it was tested on.

## What was tested

- `pytest` (145 tests, all passing on 20 Nov 2026) on the **12 synthetic PDFs
  this project generated**: per-field values against `expected.json` for the
  10 readable invoices, missing due date, malformed invoice (no guessed
  total), image-only (`no_text_layer`), duplicate detection and vendor
  normalisation, validation rules, extractor API and mock API via FastAPI
  `TestClient`.
- Both servers were started locally once and answered `/health` and
  `/payment-status`.
- Per-field accuracy, pasted from `scripts/accuracy_report.py`:

```
Per-field accuracy on 12 synthetic PDFs
field            correct/total
vendor                11/12
invoice_number        11/12
invoice_date          11/12
due_date              11/12
currency              11/12
line_items            11/12
subtotal              11/12
tax                   11/12
total                 11/12
ALL FIELDS            99/108
```

  The one miss per field is `inv_12_image_only.pdf`: nothing is extracted
  from it, by design. For the malformed invoice the true subtotal, tax and
  total are unknown, so "not extracted" counts as correct there.

  Read these numbers with care: the extractor and the test invoices were
  written together by the same author, so the rules fit these layouts.
  This shows the code does what it was designed to do, not how well it
  would do on invoices it has never seen.

- Flags on correctly read invoices are honest, not hidden: the
  letterhead layout gets `low_confidence_vendor` and
  `low_confidence_currency` (found by fallback), receipts get
  `low_confidence_line_items`, and ambiguous dd/mm dates get
  `low_confidence_*_date`. So 8 of 12 files are `needs_review: true`.

## What was not tested

- Real-world invoices from real vendors (none were used)
- Scanned PDFs / OCR (not implemented; image-only PDFs are only flagged)
- Multi-page invoices, non-English invoices, comma-decimal amounts (`1.234,50`)
- n8n, Airtable and AWS: those are later milestones (B2, B3, B4)
- Load, concurrency or security review of the APIs beyond the inbox path check
